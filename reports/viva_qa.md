Beginner-friendly answers. Numbers refer to `reports/results.json` (generated by `python -m src.train`).

## 1. Problem and data

**Q: What is phishing and why does detection matter?**
Phishing is a fake website that imitates a real one (a bank, an e-mail provider) to steal passwords or payment details.
Users usually cannot tell the difference by eye. An automatic risk estimate can warn them, or help a security team
prioritise reports.

**Q: Which dataset did you use?**
The UCI *Phishing Websites* dataset (id 327, DOI 10.24432/C51W2X, CC BY 4.0) by Mohammad, Thabtah and McCluskey (2012).
It has 11,055 rows and 30 engineered indicators, such as the presence of an IP address in the URL, the HTTPS certificate
status, and the share of anchor links that point to other domains. Each indicator is coded −1/0/1, and the label is −1/+1.

**Q: Why did you remap the labels?**
The original labels are −1 and +1. The project uses **1 = phishing, 0 = legitimate**. Logistic regression's
cross-entropy and the precision/recall definitions assume labels in {0, 1}, with 1 as the class we want to detect.
Writing the mapping down explicitly (−1 → 1, +1 → 0) prevents a silent sign error. UCI does not document which code
means phishing, so we checked the direction in the data. In all 9 "anomaly" features (e.g. an '@' in the URL), the rare
code is −1. The two strongest features also put −1 together with target −1.

**Q: What was special about the data quality?**
47% of the rows (5,206) are exact duplicates, and 64 feature vectors appear with *both* labels. We collapsed the
duplicates and dropped the conflicting vectors, which left 5,721 unique rows. We did this before splitting.
Otherwise the same row could sit in both train and test. Splitting the raw file showed that 63.6% of validation rows
had an identical twin in training.

**Q: Did removing duplicates change your results?**
Less than we expected. We retrained on the raw split as a diagnostic, and the logistic regression was not better there
(validation accuracy 0.930 vs 0.951 on clean data). The overlap was real, but these rows are easy anyway. We still report the
deduplicated numbers because they answer the honest question: how well does the model do on feature vectors it
has never seen?

## 2. Logistic Regression

**Q: What is the sigmoid function?**
σ(z) = 1 / (1 + e^(−z)). It squashes any real number into (0, 1), so the linear score z = w·x + b becomes a probability.
σ(0) = 0.5. Large positive z gives a value near 1, and large negative z gives a value near 0. In code we compute it
piece-wise, so `exp` never overflows.

**Q: What is binary cross-entropy?**
For one example, ℓ = −[y log p + (1 − y) log(1 − p)]. It is small when the model gives high probability to the true
class, and it is very large when the model is confidently wrong. We compute it as `log(1 + e^z) − y·z`, which never takes
log(0).

**Q: Derive the gradient.**
With p = σ(z) and z = w·x + b: ∂ℓ/∂p = (p − y)/(p(1 − p)), ∂p/∂z = p(1 − p), ∂z/∂w = x.
Multiplying gives ∂ℓ/∂w = (p − y)·x and ∂ℓ/∂b = (p − y). Averaging over n rows gives
∇w = Xᵀ(p − y)/n. With L2 regularisation we add λw (the bias is not penalised).
We verified the code against numerical finite differences in `tests/test_logistic_regression.py`.

**Q: How does gradient descent work, and how did you choose the learning rate?**
We repeat w ← w − η∇J. The loss is convex, so there is a single minimum. Descent is guaranteed when
η < 2/L, where L = ¼·λ_max(XᵀX/n) + λ is the smoothness constant. For one-hot inputs, 2/L ≈ 1.09. Our experiment showed
smooth decrease up to η = 1 and oscillation at 2 and 4 (`lr_02_learning_rates.png`). We searched η ∈ {0.5, 1, 1.9}/L.

**Q: Why did it need ~27,000 iterations?**
The problem is badly conditioned (condition number ≈ 730). Some levels almost perfectly separate the classes (e.g.
`prefix_suffix = 1` is never phishing), so the optimum has large weights that plain gradient descent approaches slowly.
With λ = 0 the optimum does not even exist; the weights would keep growing.

**Q: What does L2 regularisation do?**
It adds (λ/2)‖w‖² to the loss, which pulls weights towards zero. That reduces variance and keeps the solution finite.
In our regularisation path, ‖w‖ fell from 13.2 (λ = 0) to 1.4 (λ = 0.1). Validation loss was best at λ = 1e-4. Larger λ
under-fits: train and validation loss both rise (`lr_03_l2_encoding.png`).

**Q: Why is raw ternary encoding questionable for a linear model?**
Raw codes force the effect of moving from −1 to 0 to equal the effect of moving from 0 to 1, and to point the same way.
The data breaks this: for `sslfinal_state`, the "suspicious" code 0 is 99% phishing, which is *more* than −1 (89%).
One-hot encoding gives each level its own weight. It lowered validation log-loss from 0.192 to 0.139.

**Q: How do you read a one-hot coefficient?**
For each feature, the reference level is code 1 (legitimate-like). A coefficient is the change in log-odds of phishing
compared with that reference, holding the other features fixed. For example, `url_of_anchor=-1` has +6.1: rows with
mostly external or empty anchors have much higher modelled odds. This is an association in this dataset, not a cause.

## 3. Model choice

**Q: Why did you use only logistic regression?**
It is simple enough to implement, derive and verify completely by hand, its probabilities are directly usable for the
app's risk gauge, and its coefficients can be read as evidence for or against phishing. On this data it clearly beats
the best single-feature baseline (test ΔF1 +0.050 [+0.029, +0.070]) and matches a scikit-learn reference exactly.

**Q: Why is scaling unnecessary here?**
Every feature is a bounded code (−1, 0, 1), and after one-hot encoding every input is 0 or 1, so all inputs are already
on the same scale. Gradient descent's step size is set from the smoothness constant L of the actual inputs.

**Q: What can a linear model not do?**
It adds evidence feature by feature. It cannot learn that a *combination* of answers matters more than the sum of its
parts unless we engineer an interaction feature by hand. One-hot encoding already handles the non-monotone codes.

## 4. Evaluation

**Q: Define precision, recall, F1, ROC-AUC and PR-AUC.**
With phishing as the positive class:
- **Precision** = TP/(TP+FP): of the sites we flagged, how many were phishing.
- **Recall** = TP/(TP+FN): of the phishing sites, how many we caught.
- **F1** is their harmonic mean.
- **ROC-AUC** is the probability that a random phishing site gets a higher score than a random legitimate one. It does
  not depend on the threshold.
- **PR-AUC** (average precision) summarises the precision–recall curve and is more sensitive to how the positive class
  is ranked.

**Q: Why is accuracy alone insufficient?**
It hides *which* errors are made, and it depends on the class balance. The majority baseline scores 0.517 accuracy
with recall 1.0 and F1 0.68 while detecting nothing useful. For phishing, a missed attack (FN) and a false alarm (FP)
have different costs, so we report both.

**Q: How did you choose the threshold?**
On the **validation** set, by maximising F1 over thresholds 0.05–0.95: LR 0.35 (the app's 8-input model: 0.28).
The test set was not used.
A lower threshold catches more phishing but raises more false alarms.

**Q: Why might a model with higher ROC-AUC not have better precision at your threshold?**
AUC averages over all thresholds. At one specific threshold, another model can sit at a better precision/recall point.
That is why we report both threshold-free and threshold-dependent metrics.

**Q: What is data leakage, and how did you prevent it?**
Leakage means information from the evaluation data influences training. We prevented it as follows:
- We deduplicated before splitting.
- We fitted encoders on train only.
- We selected all hyperparameters and thresholds on validation only.
- Feature selection used training labels only.
- We evaluated the test set once, at the end, with frozen models.
- No column copies the label; the best single feature has validation AUC 0.898, not ≈ 1.

**Q: Why train/validation/test, and what is cross-validation?**
- **Train** fits the parameters.
- **Validation** chooses settings.
- **Test** gives an untouched final estimate. Reusing the test set for choices would make that estimate optimistic.
- **Stratified 5-fold cross-validation** on the training partition gives five estimates instead of one, so we can see
  the variability: ROC-AUC 0.990 ± 0.003, F1 0.949 ± 0.006.

**Q: How do you know a difference is real?**
We used a **paired bootstrap**: both models are scored on the same 1,000 resamples of the test set, and we take the
2.5–97.5 percentiles of the difference. LR − best single feature: F1 +0.050 [+0.029, +0.070]. Overlapping separate
intervals are not a significance test, so we did not use them as one.

## 5. Overfitting, features, interpretation

**Q: What are overfitting and underfitting? Give examples from your project.**
- **Overfitting** is a large train/validation gap. Our clearest example is the learning curve: trained on only 399
  rows, LR reaches training ROC-AUC 0.995 but validation 0.980; with all 4,004 rows the gap shrinks (0.991 vs 0.988).
- **Underfitting** is when both train and validation are poor. Two examples: λ = 0.1 (train and validation log-loss
  both 0.40) and raw −1/0/1 codes (validation log-loss 0.192 vs 0.139 for one-hot).
- Our selected LR has nearly equal train and validation F1 (0.952 vs 0.953).

**Q: Did feature selection help?**
Not for accuracy:
- Removing the 7-feature HTML/JS cluster (`favicon`, `port`, `popupwindow`, …) had no measurable effect, so 23
  features do as well as 30.
- Keeping only the top 3 features by mutual information cost about 0.03 AUC.
- Dropping `sslfinal_state` and `url_of_anchor` cost 0.071 AUC.

Feature reduction mainly simplifies the model; it does not make it more accurate.

**Q: What are the limitations of feature importance?**
- Coefficients depend on the other features in the model: correlated features share or swap weight.
- Coefficients changed sign across folds for 9 weak or redundant levels, so those should not be interpreted.
- Permutation importance spreads credit across correlated features, because shuffling one leaves its twin intact.
- Neither shows causation.

**Q: How did you verify your from-scratch code?**
- Unit tests check the gradient against finite differences.
- LR weights match scikit-learn within 1e-4 on synthetic data.
- On the real data, the maximum validation probability difference to scikit-learn is 0.016 (99.8% label agreement).
- Save/load gives identical predictions.
- On the real test set, the custom and scikit-learn models have identical F1 (no meaningful difference).

**Q: Time and space complexity?**
With n rows, d inputs and I iterations:
- **Training:** O(n·d) per iteration and O(I·n·d) in total (here I ≈ 27,000, n = 4,004, d = 38; about 14 s).
- **Memory:** O(n·d) for the data and O(d) for the model.
- **Prediction:** O(d) per row.

## 6. Limitations and the app

**Q: What are the limitations of the dataset?**
- It was collected around 2012.
- Several inputs depend on services that no longer exist or have changed (Alexa rank, public PageRank).
- The codes for some features are undocumented or ambiguous (`redirect`, `prefix_suffix`, `domain_registration_length`).
- After deduplication, the class balance does not reflect real web traffic.
- We cannot re-extract the features ourselves.

**Q: Why does the app ask only 8 questions when the model uses 30 features?**
The app uses a separate *quick* logistic regression trained on the 8 features with the highest mutual information on
the training data (HTTPS certificate, anchor links, dash in domain, sub-domains, traffic rank, form handler, links in
tags, external objects). We measured the cost on the test set: F1 0.932 with 8 inputs vs 0.937 with 30,
ΔF1 −0.005 [−0.019, +0.006] — no clear loss. So the form is 73% shorter at no measurable cost.

**Q: How did you choose the Safe / Suspicious / Likely phishing cut-offs?**
On the validation set only, with a 98% target. The lower cut-off is the highest threshold that still catches at least
98% of phishing sites, so at most 2% of phishing sites are called Safe. The upper cut-off is the lowest threshold at
which at least 98% of flagged sites really are phishing. For the app's model these are 0.17 and 0.92. On the test set,
2.1% of "Safe" sites and 98.9% of "Likely phishing" sites were phishing; 18.9% of sites fell in "Suspicious".

**Q: How are the "Why this result?" bars calculated?**
For Logistic Regression, log-odds = b + Σ w_j x_j. Each answer's bar is w_j × (x_j − average x_j in training), summed
over that feature's one-hot columns. The bars add up exactly to the site's log-odds minus the log-odds of an average
training site, so they show what moved this site away from "average". Red bars push towards phishing, green towards
legitimate. We centre on the average because, with one-hot coding, the legitimate-like answer is the reference with
x = 0, so plain w × x would never show a green bar. These are associations learned by the model, not causes.

**Q: Why is the app not a guarantee of safety?**
It outputs a *model-estimated* probability, learned from old, pre-extracted indicators. It does not inspect live
websites, and attackers adapt. Even on this dataset, the model misclassifies about 6.6% of test rows. A low score is
not proof that a site is safe.

**Q: Can I paste a URL into the app?**
No, by design. Producing these 30 indicators from a URL needs WHOIS, DNS, page-content and reputation look-ups that are
not implemented or validated, and visiting suspicious sites is unsafe. The app accepts only the 8 pre-extracted
features. (The app shows no limitations text by design; these limitations are documented in the report.)
